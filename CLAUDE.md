# CLAUDE.md

Guidance for Claude Code (or any AI agent) working in this repository. Read this before touching anything — it explains what this project is, how the pieces fit together, and a list of real bugs already found and fixed so they don't get re-introduced or re-discovered from scratch.

## What this is

A customized, self-building [Rescuezilla](https://github.com/rescuezilla/rescuezilla) live ISO + [Ventoy](https://www.ventoy.net/) USB layout, built for **PNLUG APS** (Pordenone Linux User Group). Purpose: deploy the *same pre-configured OS image* onto many PCs from *one* USB stick, unattended, safely, with no Linux knowledge required from whoever runs it.

## Repo layout

```
src/            Everything that ends up on the ISO's live desktop.
                Copied into the squashfs verbatim by build/remaster.sh — never
                edit the ISO/squashfs directly, always edit here and rebuild.
build/          build.sh (host entry point, installs Podman) and remaster.sh
                (the actual remaster logic, runs inside a pinned Ubuntu
                container). build/output/ is git-ignored (build artifact).

.github/workflows/build-and-release.yml   CI: watches upstream Rescuezilla,
                auto-builds + publishes a GitHub Release on a new tag.
```

## Architecture: one backend, two front-ends

`src/pnlug_rescue_lib.py` is the **single source of truth** for every piece of real logic: disk discovery/exclusion, size safety checks, partition growing/shrinking, backup, restore. Both front-ends — the GTK GUI (`pnlug-rescue-gui`, `pnlug-backup-gui`, sharing widgets from `pnlug_gui_common.py`) and the curses TUI (`pnlug-rescue-tui`) — call into this same module and never reimplement any of its logic themselves. **A fix belongs in `pnlug_rescue_lib.py`, not duplicated into both front-ends.**

Key conventions in that module:
- `StepResult(ok: bool, message: str, changed: bool = False)` — the return type for every operation. `changed` is `True` only when something on disk was actually modified (currently used by `shrink_system_partition_for_backup` so `backup()` knows whether it needs to grow the source back afterward — a no-op shrink like "already small enough" must never trigger a regrow, since nothing was touched).
- `LogFn = Callable[[str], None]` — every long-running function takes a `log` callback instead of printing directly, so the GUI can stream it into a text view and the TUI into a curses pane with the same calls.
- `run_streaming(args, log, success_marker=None, stdin_text=None)` — the one place that shells out to external commands with live log streaming. Reads on a background thread and waits on `proc.wait()`, not pipe EOF (see the Known Gotchas list — pipe EOF can hang forever here). `success_marker` exists because the stock `rescuezilla` wrapper has its own exit-code bug (see below) — pass the real success string to look for instead of trusting the process exit code.
- `resolve_mountable(partition_path)` — always call this before mounting a Ventoy/system partition. Real Ventoy sticks wrap partitions in device-mapper nodes on a full desktop boot; the raw `/dev/sdX1` path is often "busy." It falls back from the `/dev/mapper/<name>` symlink to `/dev/dm-N` (via `dmsetup info`) because that symlink is non-deterministic — confirmed live, repeatedly, that the dm device itself always exists but udev sometimes just never creates the symlink for it.
- `find_system_partition(disk)` identifies the Linux root **by content** (`/etc/fstab` + `/usr/bin` or `/bin`), never by size or position. Don't regress this to a size-based heuristic.
- `_inspect_mounted_partition(part, check_fn, scratch_mnt)` — the pattern every "find a partition by inspecting its contents" function (`find_system_partition`, `detect_distro_name`, `find_ventoy_partition`) must use: check `findmnt` for an existing mountpoint and inspect *there* instead of mounting fresh, and don't skip a candidate just because it's already mounted. A version that skipped already-mounted candidates outright silently failed to identify the one partition it actually needed, right after a real restore (see gotcha #12).
- `_ensure_partition_free(part)` — call this before any `parted`/`sfdisk` call that needs the kernel to actually apply a partition table change (growing/shrinking). Unlike the read-only tolerance above, a *write* to a busy partition can update the on-disk table while the kernel/filesystem view silently doesn't follow (see gotcha #13) — this unmounts the partition's whole mount tree first instead.
- `ensure_root()` — every entry point (`pnlug-rescue-gui`, `pnlug-backup-gui`, `pnlug-rescue-tui`) calls this immediately after importing `pnlug_rescue_lib`, before importing anything GUI-related. It re-execs itself under `sudo -n -E` if not already root. **Do not add a new entry point without calling this first** — none of the launch paths elevated privileges before this existed, so every real disk operation silently failed on a genuine unprivileged desktop login (see gotcha #11).

`pnlugrescue.sh` is the original bash-only implementation, kept on the ISO for CLI/manual use and backward compatibility. It is **not** the thing to edit for behavior changes — `pnlug_rescue_lib.py` is authoritative for the GUI/TUI, which is what real users actually use.

## Autostart chain

`src/pnlug-autostart.sh`: GUI → TUI (in a terminal) → visible error dialog, in that order. A normal close of the GUI (user finishes or just closes the window) is success, not a failure — only "couldn't even start" triggers the fallback.

**Do not assume this release's live session uses `xfce4-session` or `gnome-session`.** It runs plain `openbox-session`, which never reads `/etc/xdg/autostart/*.desktop` at all (confirmed live — the freedesktop autostart entry silently never fired). The real entry point is a line `build/remaster.sh` appends directly into `/etc/xdg/openbox/autostart`. The `.desktop` entry is kept too, purely in case a future Rescuezilla release switches session managers — don't rely on it alone, and don't remove the openbox hook.

## Build system

`build/build.sh [codename]` → installs Podman if missing → runs `build/remaster.sh` inside a pinned `ubuntu:24.04` container. `remaster.sh` fetches the latest matching upstream Rescuezilla ISO, extracts it, unpacks/patches/repacks the squashfs, patches `boot/grub/grub.cfg`, and rebuilds the ISO with `xorriso`'s boot-image-replay feature. Read `docs/build-guide.md` for the step-by-step; read the script itself (it's short and heavily commented) before changing it.

CI (`.github/workflows/build-and-release.yml`) runs the same `build.sh` on a schedule, skips if a release for the current upstream tag already exists, and publishes a GitHub Release (`rescuezilla-<upstream-tag>`) with `pnlug_zilla.iso` + `ventoy.zip` attached when it's genuinely new.

## Known gotchas — read before "fixing" these again

These were each found through real, live QEMU/OVMF testing, not guessed. If you see the symptom again, this is almost certainly why:

1. **`unsquashfs` prints `create_inode: failed to create character device ... Operation not permitted`** for a handful of `/dev/*` entries, and exits 2. This is expected in rootless containers (no capability grants real `mknod` for device nodes) and harmless (`devtmpfs` replaces `/dev` at boot anyway). `remaster.sh` explicitly tolerates exit code 2 specifically — do not "fix" this by chasing full root/privileged containers; a *different* nonzero exit code should still fail the build.
2. **`parted -s resizepart` to a *smaller* size cannot be scripted** — its "Shrinking a partition can cause data loss" confirmation is not bypassable via stdin in script mode, tried multiple ways. Use `sfdisk -N <partnum> --no-reread <disk>` with `", <newsize>M\n"` on stdin instead (see `_shrink_partition_to`). Growing (`resizepart ... 100%`) works fine with plain `parted -s`.
3. **`xorriso`'s boot-image-replay breaks if you `-map` the whole extracted tree.** It needs the original ISO's own boot-catalog-referenced files (El Torito images, GRUB2 MBR patch) to resolve by reference to the *original* image, not fresh local copies at the same paths. Only `-map` the specific files you actually changed (squashfs, its size sidecar, `grub.cfg`) — see `remaster.sh`'s comments at the final `xorriso` call.
4. **The stock `rescuezilla` CLI wrapper has its own exit-code bug**: after a genuinely successful restore/backup, its cleanup path calls `systemctl --user --runtime unmask --quiet --` with no unit names, which `systemctl` rejects, and that becomes the wrapper's own (wrong) exit code. Don't trust the wrapper's exit code alone — `restore()` checks for the real "Successfully restored image partition" success marker; `backup()` checks that the actual output file exists and is non-empty.
5. **`run_streaming` must wait on `proc.wait()`, not pipe EOF.** Some unrelated long-lived process the wrapper touches (suspected `systemd-udevd`) can inherit the pipe's write end and hold it open even after the real child has exited, so `for line in proc.stdout` can hang forever. Read on a background thread, wait on the process directly, then force-close the pipe.
6. **A GTK bug can silently freeze the UI at the last log line with zero error output**: an exception thrown inside a `GLib.idle_add` callback is swallowed by GLib, not raised anywhere visible. If a progress page appears to hang after real backend work has clearly finished (check `/proc/<pid>/task/*/wchan` — if every thread is idle, nothing is actually blocked), suspect a bug in the idle callback itself before suspecting the subprocess layer.
7. **A log file `rm -f`'d and recreated, not truncated in place.** `pnlug-autostart.sh`'s log removes-then-creates rather than truncating, because a stale file from a *different* user context (the live session's normal user vs. a root maintenance shell) can be un-truncatable by the other but is always unlinkable (only needs directory permission). A failed redirect target stops the whole redirected command from running, not just the logging — this silently broke the entire GUI→TUI→error chain before the fix.
8. **`toram` alone isn't enough for a Ventoy stick — pair it with `noeject`.** Casper's default RAM-boot behavior can interfere with mounting *other* partitions on the same physical stick afterward (like the one holding `restoreimg/`). `noeject` stops it from trying to detach the boot medium once copied to RAM. `remaster.sh` sets both together when it switches the default grub entry.
9. **Backup's pre-shrink must always be undone afterward, but only if it actually happened.** `shrink_system_partition_for_backup`'s `StepResult.changed` flag exists specifically so `backup()` can tell a real shrink apart from a no-op — growing back an already-correctly-sized disk would be a *new* bug in the other direction.

The following were found on **real hardware**, not the VM — the VM's disposable, always-root, always-fresh-boot setup never exercised a genuine unprivileged live-session login, a real physical Ventoy stick's device-mapper quirks, or a real disk's pre-existing partition layout. Treat "it passed in the VM" as necessary, not sufficient, for anything touching privilege, mounting, or partition-table writes.

10. **Ventoy's own secondary "Boot in normal mode / grub2 mode / File checksum" menu still asks for Enter even with `VTOY_MENU_TIMEOUT` set** — it's a *separate* menu with its own timeout knob. Fix is `"VTOY_SECONDARY_BOOT_MENU": "0"` in `ventoy/ventoy.json`'s `control` array (disables it outright, since we never want the alternatives), not a timeout tweak. Rescuezilla's *own* extracted `boot/grub/grub.cfg` has a separate `set timeout=10` again after that — `remaster.sh` `sed`s it down to `set timeout=1` (with a grep guard that fails the build if the line isn't found, so an upstream format change doesn't silently no-op the patch).
11. **None of the launch paths (autostart, or any Desktop shortcut) ever elevated to root.** Every real disk operation was silently failing on a genuine unprivileged desktop login — `find_ventoy_partition()` run as plain user returned `None` in 0.03s (no error, just nothing found), while the exact same call as root resolved correctly in 0.2s. Fixed by `ensure_root()` (see above) — call it, don't reinvent it per-entry-point.
12. **`find_system_partition`/`detect_distro_name` used to skip a partition outright if it was already mounted elsewhere**, instead of inspecting it in place like `find_ventoy_partition` already did. Root cause it collided with: rescuezilla's own post-restore chroot-test step mounts the just-restored partition at `/tmp/root_reinst.XXXXXX` (with `/sys` and `/sys/firmware/efi/efivars` bind-mounted inside it for the chroot) and its own cleanup can fail to fully unmount it — confirmed live, repeatedly, same leftover mount tree after multiple separate restores. Symptom: "Could not identify a Linux system partition — restore succeeded, but auto-grow was skipped" immediately after a restore that had just visibly worked. Fixed via `_inspect_mounted_partition` (see above).
13. **A *write* to a busy/mounted partition can silently half-apply.** `parted resizepart` printed `Partition /dev/sda2 is being used. Are you sure you want to continue?` against the same leftover chroot-test mount from #12, and with the kernel unable to apply the new size to a busy partition, the on-disk GPT entry changed while the filesystem/kernel view of the partition's size did not — `grow_system_partition` reported "Filesystem resized successfully" but a follow-up `e2fsck` still saw the pre-grow geometry. Fixed by `_ensure_partition_free`/`_unmount_tree` (see above), called before the `parted`/`sfdisk` call in both `grow_system_partition` and `_shrink_partition_to`.
14. **`blkid` immediately after `partprobe` can return empty**, same race class as `find_system_partition` right after a restore (both need `udevadm settle --timeout=10` between the two) — confirmed live: `parted resizepart` grows the partition table entry correctly, but the immediately-following `blkid` call in the same function came back with `TYPE=""` on an unquestionably-ext4 partition, reported as "Unsupported filesystem type ''". A `blkid` run one second later on the same partition was correct.
15. **The `/dev/mapper/<name>` symlink for a Ventoy stick's data partition doesn't always get created**, even though the underlying dm device always does (`dmsetup ls` always shows it) — confirmed on both the VM and real hardware, non-deterministically. `resolve_mountable` falls back to `dmsetup info -c --noheadings -o minor <name>` → `/dev/dm-N`. Related: the dm-wrap device itself can take **minutes** to appear right after boot under load (`toram` copying simultaneously) — `find_ventoy_partition`'s retry budget is 300 (~5 min), don't shrink it back down without re-confirming that's no longer needed.
16. **`is_last_partition()` (strict "is this the last partition on the disk") wrongly refused to grow a system partition followed by an ordinary swap partition.** A real restore left an actual `/dev/sda2` stuck at its shrunk backup size with a large unreachable gap after it. Replaced with `_grow_target_end()`, which computes the exact safe `parted resizepart` target sector from the real partition table (`sfdisk -d`) instead of a boolean last/not-last check — the fix threads through any layout, not just "swap after root."
17. **partclone prints two different live-progress line formats**, and only one was ever parsed by name. `"Elapsed: HH:MM:SS, Remaining: HH:MM:SS, Completed: NN.NN%, Rate: X/min"` was always recognized; `"Current block: N, Total block: M, Complete: NN.NN%"` (seen on small FAT/swap partitions, and which rescuezilla's own wrapper doesn't recognize either — it forwards the raw line, sometimes prefixed `"Not yet interpreting partclone output: "`) was only ever caught by chance via a generic bare-`%` fallback regex. Parse rescuezilla's own forwarded output by its actual formats, don't lean on a loose catch-all as the primary path. Similarly, `resize2fs -p`'s own progress is a fixed-width dash/X text bar (`"Relocating blocks    ----------XXXXXXXXXX"`), not a digit percentage at all — needs its own parser, not the generic percent regex.
18. **A restore can leave the restored root filesystem without a `/dev` directory at all**, and the very next boot kernel-panics before anything can run (confirmed live; fixed by hand once with a manual `mkdir /dev` from a chroot before the code fix existed). Upstream cause (rescuezilla's own restore step, or partclone itself) not confirmed, but there's no safe way to boot without it — `ensure_essential_directories()` runs right after every restore and creates `/dev`, `/proc`, `/sys`, `/run`, `/tmp` on the restored root if any are missing, logging a clear warning when it has to.
19. **The stock Rescuezilla welcome wizard can auto-launch alongside ours via `/home/ubuntu/.xprofile`'s own `rescuezilla &` line**, leaving a stray `rescuezillapy` process that makes our own restore/backup fail outright with "Only one rescuezillapy process is permitted." `build/remaster.sh` strips that line from the extracted `.xprofile` — don't re-add a plain `rescuezilla &` anywhere in the boot chain.

## Testing methodology

There's no automated test suite — every change above was verified against a real, disposable QEMU/OVMF VM: a genuine Ventoy USB image, disk images of differing sizes, a real installed Linux distro backed up and restored across them, and deliberately-broken scenarios (missing binaries, wrong permissions, undersized destinations, Secure Boot on) to confirm safety checks and fallbacks actually behave as designed. This rig isn't checked into the repo (it's disposable, multi-GB test images), but the shape of it is:

- OVMF UEFI firmware (`edk2-ovmf` on Fedora/RHEL, `ovmf` on Debian/Ubuntu)
- A real Ventoy-installed USB image (`qemu-img create -f raw ventoy.img <size>`, then run Ventoy's own installer against it via a loop device, or against a real stick and `dd` it off)
- One or more blank/pre-installed disk images of different sizes to exercise backup/restore/grow across genuinely different disk geometries
- QEMU's QMP socket (`-qmp unix:qmp.sock,server,nowait`) for scripted screendumps and input injection — useful for driving the GTK GUI through a full flow non-interactively
- A `-virtfs` 9p share for pushing updated files into a running guest without rebuilding the ISO each iteration

When testing a `pnlug_rescue_lib.py`-only change, you don't need a full ISO rebuild: copy the updated file into a running guest via the 9p share (or however you're getting files in) and re-run against it directly — much faster than the ~15–20 minute full build cycle. Only rebuild the ISO to verify a `remaster.sh`/packaging-level change, or right before cutting a release.

**A VM pass is necessary, not sufficient — see the real-hardware gotchas above (#10–19).** A disposable QEMU VM is typically booted fresh and driven from an already-root context, which never exercises: a genuinely unprivileged live-session login, a real Ventoy stick's device-mapper/udev timing, or a disk that already has a real, "messy" partition layout (existing swap, odd gaps, an already-shrunk partition from a prior run). Every one of those surfaced a real bug that every prior VM pass had missed. When real hardware is available (over SSH, with the user's explicit go-ahead each time — this is someone's actual machine, treat the access accordingly), the workflow that found and fixed all of them was:
1. Diagnose live against the real machine (direct SSH command, not guessing from a log).
2. Fix in `pnlug_rescue_lib.py`, syntax-check + run `python3 pnlug_rescue_lib.py` (the self-check), adding a case using real captured data where the fix can be tested without a live block device — see `_self_check()`'s `_create_missing_essential_dirs`/`_grow_target_end` cases for the pattern (pure logic factored out and tested against synthetic/real data, the mount/disk I/O left thin and untested).
3. Hot-patch the single file via `scp` onto the live machine (`/usr/bin/pnlug_rescue_lib.py`) and re-verify immediately — **note the fix doesn't take effect until the GUI process is restarted**, since the module is only imported once per process; killing and relaunching it goes through the normal `pnlug-autostart.sh` fallback chain (GUI failure → TUI) if killed uncleanly, so relaunch `pnlug-rescue-gui`/`pnlug-backup-gui` directly with the same env autostart uses (`DISPLAY=:0`, `XAUTHORITY=<user's home>/.Xauthority`, `XDG_RUNTIME_DIR=/run/user/<uid>`) rather than just re-running the autostart script.
4. Commit and push.
5. Rebuild the ISO, verify the fix is actually baked in (mount the ISO read-only, `unsquashfs` just the changed file(s) out of `casper/filesystem.squashfs`, `grep` for the fix, run the self-check against the extracted copy) before trusting the rebuild.
6. Upload to the GitHub Release (`gh release upload rescuezilla-<tag> pnlug_zilla.iso ventoy.zip --clobber`) and update the release notes (`gh release edit`).
7. If a physical Ventoy stick is available locally, copy `pnlug_zilla.iso` + `ventoy/theme` + `ventoy/ventoy.json` onto it directly and `md5sum` both copies of the ISO to confirm the write wasn't truncated/corrupted.

## Licensing note

Rescuezilla is GPLv3. This project only ever *adds* separate files alongside Rescuezilla's own (desktop entries, our own scripts, branding) — it never modifies Rescuezilla's own source or binaries. That's "mere aggregation" under GPLv3 §5, which is why the PNLUG-authored code here can carry its own MIT license (see `LICENSE`) without pulling the whole ISO under GPL. If you ever start patching Rescuezilla's *own* files (not just adding new ones next to them), re-check this reasoning before shipping it.
